# Codex implementation prompt — AMSA AIU Election 2026

You are the full-stack engineer. The attached folder is the existing **frontend-only design and PIN demo** for AMSA AIU Election 2026. Build a **complete, functional election app** using **plain PHP 8.2+, PDO, MySQL/MariaDB, HTML/CSS/vanilla JS/Bootstrap**, developed locally using **XAMPP** and deployable to standard **Hostinger PHP/MySQL hosting**. **Do not redesign the frontend**; preserve layout, pages, CSS, assets, responsiveness, and user flow. Work directly on this repo; create the actual files rather than only describing code. Avoid Node-dependent production servers, Supabase, Laravel, Next.js, and external authentication services.

## Official flow

On event day: voter arrives -> attendance confirmed by physical counter -> authorized AMSA admin creates voter with **full name + Student ID (AIU followed by digits)** -> cryptographically secure **six-digit PIN**, including leading zeros, automatically generated (optional admin manual entry/re-generate) -> PIN shown **once**, copied/handed directly to voter. Voter signs in using Student ID + PIN -> selects **exactly one candidate for ALL five positions**, in this fixed order: **Female Treasurer, Male Treasurer, Secretary, Vice President, President**. Both male and female treasurers must be voted on by every voter. Review -> final confirmation -> immutable anonymous vote -> account marked VOTED -> voter cannot vote again for that round. Candidates may vote too. Staff can reset a PIN only **before** the person has voted, after verifying their identity in person. NO public account registration, email confirmation, or voter self-service PIN reset. Admins see results while voting; voters cannot see any vote counts until publication. Admin controls opening/closing the ballot and publishing/hiding results. Tie means a deliberate, auditable **runoff/revote round for tied position(s)**, not silently choosing a winner.

## Mandatory implementation order

**PHASE 1 — Database first:** Create `database/schema.sql` (MySQL 8 / XAMPP MariaDB-compatible UTF8MB4 InnoDB; all PK/FK/UNIQUE/indexes), `database/seed.sql` (five positions and safe fictional sample candidates, not real votes), and document an ERD/table relationships. Use tables at least: `admins` (id, username unique, password_hash, role, active); `elections` (id, title, voting/status fields, publication flag); `election_rounds` (election_id, round number, type normal/runoff, status); `positions` (id, election_id, name/slug unique per election, display_order); `candidates` (id, position_id, Student ID, name, manifesto, photo path, active); `voters` (id, unique Student ID, full_name, pin_hash, status, created_by, created_at); `voter_participation` (unique voter_id+round_id, has_voted/voted_at); `anonymous_ballots` (id random UUID, round_id, submitted_at; **NO voter_id or student ID**); `ballot_choices` (ballot_id, position_id, candidate_id, UNIQUE ballot_id+position_id); `admin_audit_logs` (action, actor, timestamp, NO ballot selections); plus `login_attempts` or robust rate-limiting equivalent. Include required keys and sensible delete restrictions. Track runoff eligibility/positions independently. Do not store or expose a direct voter-to-ballot mapping, even in audit logs. Explain operational limits of anonymity and avoid logging vote payloads.

**PHASE 2 — PHP backend:** Implement configuration (`.env.example`/config outside public exposure), PDO DB connection, PHP session bootstrap, standardized JSON response/error helpers, CSRF, routing or separate PHP endpoints, and auth/permission guards. Keep everything same-origin. All SQL **prepared statements**; validate on server regardless of frontend. Endpoints/features: admin login/logout/session; create/list/search/enable/disable voters; generate/reset PIN; candidate CRUD with validated safe photo upload; election status/start/stop/results publication; voter login/logout/session; read allowed positions/candidates; submit ballot; admin totals/turnout/dashboard; public results gated behind publication; projector reveal gated by admin/publication policy. Return consistent JSON `{ok:true,data:...}` or `{ok:false,error:{code,message}}`, proper HTTP status, and never serialize `pin_hash`. No request should return an old PIN. Implement initial admin creation as **CLI-only seed/setup** with no public default password. Candidate creation and voter creation must be supported even with no preloaded student roster.

**PHASE 3 — Atomic voting:** For `POST /api/vote/submit` (or a documented equivalent), require a valid voter session and active election/round; inside one DB transaction lock/check the voter’s participation row with `SELECT ... FOR UPDATE` (or a correct locking strategy), reject already-voted/disabled voters, validate exactly one allowed active candidate for each eligible position, insert one anonymous ballot + associated choices, mark participation voted, then COMMIT. Concurrent, repeated, or replayed submissions cannot create extra ballots. No vote editing, no partial vote, no ballot data returned to the voter after submission. If voting has closed, reject submits server-side. Runoff ballots cover only tied positions and permit at most one vote per voter per runoff round. Add tests for simultaneous submissions.

**PHASE 4 — Integrate existing frontend:** Replace the browser-only `js/demo-store.js` and fake hardcoded results/candidates/status with a documented `js/api.js` (`fetch` + credentials/session/CSRF) and page-specific bindings. Keep existing design and working modals, PIN generation/preview/handoff, form validation, filters, ballot review, and responsive layout. Server remains authoritative. Remove `demo-admin` credentials, fake sample counts, local PIN storage, pretend sessions, and disabled placeholder forms from production. Convert `/user/register.html` and `/user/reset-password.html` to in-person-counter information pages or remove their public links; only admin creates accounts and resets PINs. Show server-retrieved voter name/status and only publish results when authorized. Fix and document URLs for XAMPP subdirectory and Hostinger root deployment. Render user-supplied names/manifestos safely (no unsanitized `innerHTML`).

**Security and privacy (non-negotiable):** Generate PINs with `random_int(0,999999)` + 6-digit padding; server hashes PINs with `password_hash` after HMAC-ing with a server-only secret pepper (or equivalent hardened approach for six-digit PINs), check via `password_verify`; rate-limit/temporarily lock repeated login attempts per account and IP; generic login failure messages; HTTPS in deployment; `HttpOnly`, `Secure` in HTTPS and `SameSite=Lax/Strict` session cookies; `session_regenerate_id` on login, session invalidation on logout; CSRF on state changes; server-enforced admin/super-admin roles; output escaping, strict input validation, safe uploads outside executable paths, no secrets in Git, protected error logs; confirm sensitive admin actions; secure deployment headers. Protect real student information; no analytics of vote selections. Implement server-side timestamping and admin action audit without vote-choice leakage.

**Testing and deliverables:** Provide `README-XAMPP.md` with exact import and XAMPP steps, `.env.example`, CLI admin setup, `.sql` files, all PHP endpoints, integrated JS/HTML, a short API contract, manual E2E checklist plus executable PHP/JS tests where feasible. Test: duplicate Student ID, PIN leading zeros, wrong PIN/throttling, disabled account, lost PIN reset, once-voted reset denial, voter auth and role guards, five required choices, candidate/position tampering, open/close, hidden/public results, concurrent double-submit, anonymous rows with no voter link, ties/runoff, admin results and reveal. Use fictional seed data. Verify on actual XAMPP/MySQL if available; otherwise say clearly what is NOT tested. Stop only once the entire login -> vote -> results workflow is implemented and all feasible tests pass. Summarize changed files and remaining deployment steps; do not claim production readiness without a security review/rehearsal.
